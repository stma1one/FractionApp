# FractionApp

מדריך זה מסביר את העיצוב סביב שימוש בממשקים (interfaces) בפרויקט — בעיקר סביב הממשק `ICalculatable` וה-`IComparable`. המסמך מסביר מה המשמעות של "ממשק כחוזה", מה נדרש ממחלקה החותמת על החוזה, ולמה במערכת שלנו `ICalculatable` משתמש ב-`object` כקלט ותוצאה. בנוסף יש הסבר על חוזים מובנים ב-.NET (דוגמאות) והסבר על יצירת מערכים מטיפוס ממשק ועל פעולת השוואה במחרוזות.

---

## 1. הגדרה: ממשק כ"חוזה"

ממשק (interface) מתואר כ"חוזה" בין המשתמש/הקוד לקריאה לבין המחלקה שמממשת אותו:
- החוזה מגדיר אילו פעולות (שיטות), אירועים או תכונות זמינות ומה החתימות שלהן (שם, פרמטרים, טיפוס חזרה).
- מי שמממש את הממשק מתחייב למלא את החוזה — כלומר להציע מימוש תקין לשיטות המוצהרות.
- קוד שמסתמך על הממשק יכול לפעול נגד כל אובייקט שמיישם אותו, בלי לדעת את מימוש הפנימי.

יתרון מרכזי: הפרדה בין ממשק למימוש -> הנדסת תוכנה מודולרית, בדיקות קלות יותר, החלפה/הרחבה של מימושים ללא שינוי בקוד הצורך.

---

## 2. מה נדרש מהמחלקה החותמת על החוזה (ICalculatable)

בהנחה שהממשק מוגדר בקווים כלליים כך:

```csharp
public interface ICalculatable
{
    object Calculate(object other);
}
```

המחלקה החותמת על `ICalculatable` חייבת:
- לממש את השיטה `Calculate` (או כל שיטה אחרת שמוגדרת בחוזה) בדיוק לפי החתימה.
- לקיים את ההבטחה ההתנהגותית של החוזה — כלומר, לתת תוצאה צפויה ויציבה עבור קלטים נתמכים, ולזרוק שגיאה מסודרת (למשל `InvalidOperationException` או `ArgumentException`) כאשר הקלט אינו נתמך.
- לא להסתמך על מצב פנימי לא מתועד שמפר את החוזה — כל התנהגות מיוחדת חייבת להיות מתועדת.

דוגמה למימוש פשוט של `Fraction`:

```csharp
public class Fraction : ICalculatable, IComparable
{
    public int Numerator { get; }
    public int Denominator { get; }

    public Fraction(int n, int d) { /* בדיקות, קיצור שבר וכו' */ }

    // דוגמה איטית אך ברורה: Calculate מבצע חיבור עם אובייקט אחר אם הוא תומך בכך
    public object Calculate(object other)
    {
        if (other is Fraction f) {
            // החזר Fraction חדש
            return Add(f);
        }
        if (other is int i) {
            return Add(new Fraction(i, 1));
        }
        throw new InvalidOperationException("לא ניתן לחשב עם סוג זה");
    }

    private Fraction Add(Fraction other) { /* החזר סכום */ }

    // מימוש IComparable (להלן)
    public int CompareTo(object obj) { /*...*/ }
}
```

חשוב לתעד אילו סוגים הנתמכים ומה ההתנהגות לציפיות שונות (למשל האם Calculate משנה את האובייקט הנוכחי או מחזירה מופע חדש).

## 3. למה ICalculatable מקבל ומחזיר object ולאו דווקא Fraction

הסיבות העיקריות לשימוש ב-`object` בחתימה:
- גמישות בין-טיפוסית: מאפשרת ליישם חיבור/חישוב בין טיפוסים שונים (Fraction עם int, Fraction עם double, או עם סוגים אחרים).
- תמיכה בהרחבה עתידית: ניתן להוסיף סוגים חדשים שמיישמים חוזה זה מבלי לשנות את החתימה.
- ירושה מממשקים קיימים או שימוש ב-reflection/דינמיות: לפעמים הרצון הוא לאכוף חוזה ריצה כללי.
- תאימות עם ממשקי .NET ישנים שלא השתמשו בגנריות.

מה חשוב לזכור כשמשתמשים ב-`object`:
- יש צורך בבדיקות-סוג (type checks / pattern matching) בתוך המימוש, ולזרוק חריגה כאשר סוג אינו נתמך.
- שימוש ב-`object` עלול לגרום לצורך ב-boxing/unboxing ובאובדן בטיחות טיפוס בזמן קומפילציה — שקול להציע גירסה גנרית (כמו `ICalculatable<T>`) אם בטיחות טיפוסים חשובה.
- תיעוד ברור: יש לתעד מהן הציפיות לגבי טיפוסים נתמכים על מנת שלא יווצרו אי הבנות למתממשים.

החלופה המומלצת לעתים היא ממשק גנרי:

```csharp
public interface ICalculatable<T>
{
    T Calculate(T other);
}
```

זה נותן בטיחות טיפוס בזמן קומפילציה אך מפחית את הגמישות בין טיפוסים שונים.

## 4. חוזים מובנים במערכת (דוגמאות)

ב-ecosystem של .NET קיימים מספר ממשקים סטנדרטיים (חוזים מובנים) ששווה להכיר:
- IComparable / IComparable<T> — להשוואה בין אובייקטים (מימוש CompareTo).
- IEquatable<T> — לביצוע בדיקות שוויון חזקות יותר ממימוש Equals.
- IEnumerable / IEnumerable<T> — מאפשר איטרציה עם foreach.
- IDisposable — חוזה לניקוי משאבים.
- IFormattable — תמיכה בעיצוב מותאם.
- ICloneable — חוזה לשכפול/שכפול שטחי.

כדאי להסתכל על הממשקים הללו כעל חוזים שמייצגים יכולות סטנדרטיות שמרבית הספריות והממשקים האחרים יודעים להשתמש בהם (למשל אלגוריתמים של מיון משתמשים ב-IComparable).

## 5. מה החוזה של IComparable

`IComparable` או הגרסה הגנרית `IComparable<T>` מגדירים שיטה יחידה:

- חתימה (לא גנרי):
  ```csharp
  int CompareTo(object obj);
  ```
- חתימה (גנרי):
  ```csharp
  int CompareTo(T other);
  ```

חוזה ההתנהגות:
- החזרת ערך שלילי => האובייקט הנוכחי קטן מ-obj.
- החזרת אפס => שווים.
- החזרת ערך חיובי => האובייקט הנוכחי גדול מ-obj.

מחלקה המממשת חייבת:
- להחזיר תוצאות עקביות (אם A < B וה-B < C אז A < C).
- להחזיר 0 אם Equals מחזיר true (מומלץ לשמור על עקביות בין CompareTo ל-Equals).
- לטפל במקרים בהם obj הוא null (בדרך כלל כל אובייקט נחשב גדול מ-null, כלומר החזרת חיובי).

דוגמה פשוטה ל-CompareTo ב-Fraction:

```csharp
public int CompareTo(object obj)
{
    if (obj == null) return 1;
    if (!(obj is Fraction other)) throw new ArgumentException("ציפו ל-Fraction");

    // השוואה על בסיס cross-multiply כדי להימנע מעיגול:
    return (this.Numerator * other.Denominator)
         .CompareTo(other.Numerator * this.Denominator);
}
```

## 6. בתוכנית הראשית — למה ניתן לייצר מערך מטיפוס החוזה ואיך Comparable במחרוזת עובד

יצירת מערך מטיפוס ממשק מאפשרת אחסון אובייקטים שונים שמיישמים את אותו חוזה. דוגמה:

```csharp
ICalculatable[] arr = new ICalculatable[]
{
    new Fraction(1, 2),
    new SomeOtherNumericType(...),
    new Fraction(3, 4)
};
```

למה זה עובד:
- המערך מאחסן הפניות לאובייקטים; כל מופע שמממש את `ICalculatable` עומד בדרישה של החוזה ולכן יכול להישמר שם.
- כשקוראים לשיטה כמו `Calculate` על איבר במערך, הקריאה מתבצעת פולימורפית (runtime dispatch) אל המימוש המתאים של אותו מופע.

השפעה מעשית:
- מאפשר קוד כללי העובד על "יכולות" (Capabilities), לא על מימוש ספציפי.
- קל לתזמר פעולה על כל האובייקטים במערך בלי לדעת את הסוג המדויק שלהם.

כיצד Comparable במחרוזת עובד:
- ב-.NET, `string` מממשת `IComparable<string>` (וגם `IComparable`), והשיטה `CompareTo` משווה מחרוזות בדרך כלל לפי סדר לקסיקוגרפי.
- חשוב: יש שתי אופציות של השוואת מחרוזות — תרבותית (culture-sensitive) ו-ordinal. ברירת המחדל של `string.CompareTo` היא התרבותית לפי סביבת התרבות הנוכחית, מה שעלול להוביל להבדלים סביבתיים. אם רוצים התנהגות עקבית בין סביבות, השתמשו ב-`StringComparer.Ordinal` או `string.Compare(..., StringComparison.Ordinal)`.

דוגמה: מיון מערך מחרוזות יפעיל את CompareTo של כל מחרוזת:

```csharp
string[] words = { "apple", "Banana", "apricot" };
Array.Sort(words); // שימוש ב-IComparable<string> של string
```

התוצאה תלויה בכללי השוואה תרבותיים; אם רוצים מיון שאינו תלוי בתרבות ושומר על סדר ASCII/Unicode פשוט — השתמשו ב-`Array.Sort(words, StringComparer.Ordinal)`.

## סיכום והמלצות עיצוביות

- ממשק = חוזה: הגדרו בבירור את החתימות וההתנהגויות המצופות.
- שימוש ב-`object` נותן גמישות אך מפחית בטיחות טיפוסים; שקלו ממשק גנרי אם המקרה עומד לכך.
- תמיד תיעדו אילו טיפוסים נתמכים ומה יקרה במקרים לא נתמכים (חריגות).
- שמרו עקביות בין CompareTo ל-Equals וכתבו בדיקות יחידה המשוות התנהגויות קצה.
- אם יש צורך בפעולות חישוביות רבות (חיבור, חיסור ועוד) שקלו להגדיר ממשק עם שיטות ספציפיות (`Add`, `Subtract`, ...) במקום שיטה אחת כללית `Calculate`.
